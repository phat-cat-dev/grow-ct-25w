## 1. The hierarchy (your "course view > nav > page > article > block > cards > component")

The Adapt content model, exactly as this repo implements it:

```
Course
 └─ Content Object  (_type: "page" | "menu")        ← the "page" (= lesson title)
     └─ Article     (_type: "article")              ← a "phase" (intro / middle / end)
         └─ Block   (_type: "block")                ← the container; where "cards" live
             └─ Component (_type: "component")       ← the inner working
```

Your gloss maps onto real repo artifacts like this:

| Your term | Repo implementation |
|---|---|
| course view / nav + buttons (your version) | `src/extensions/adapt-ab-navigation` (custom nav/buttons) + `config.json._navigation`; button CSS in `exports/theme-css/ab-buttons.css` / `src/extensions/adapt-ab-theme/less/ab-buttons.less` |
| page (= lesson title) | contentObject `_type:"page"`, `_parentId:"course"` |
| article (= phase: intro / middle / end) | `_type:"article"` with phase classes (§3) |
| block (container for components) | `_type:"block"`, carries `_skeletonKey` + `_trackingId` (§4) |
| **cards** at block level | **`src/components/adapt-ab-card`** component; styling in `src/extensions/adapt-ab-theme/less/ab-cards.less` → `exports/theme-css/ab-cards.css` |
| component (inner working) | `_type:"component"`, a `_component` plugin (§5) |

Authored as JSON under `courses/<slug>/`:
`config.json` (root) + `en/{course,contentObjects,articles,blocks,components}.json`.
Every element needs a unique `_id` and correct `_parentId`; integrity is checked by
`tools/verify-course.js`.

## 2. Page types ("skeletons" / your "shapes" — sense A)

There are **6 page archetypes**, defined in `design-kb/design-kb.skeletons.json`
(schema `schemas/design-kb.skeletons.schema.json`), generated by
`tools/generate-course-shell.js` via the `/scaffold` skill. Fixed course page sequence:

| Order | Page type (`pageType`) | baseKey | Articles | Role |
|---|---|---|---|---|
| 1 | `wrapper-open` | `W-OPEN` | single | overview, learning-outcomes, practice-connection, signpost, course-instructions, course-conventions |
| 2 | `c-pre` | `C-PRE` | single | confidence-pre survey ("Before you start") |
| — | `lesson` | `L01…L0n` | **multi (5)** | the teaching unit — inserted between C-PRE and SUMM, one page per lesson |
| 3 | `summative` | `SUMM` | single | introduction, assessment-items, results ("Test your learning") |
| 4 | `c-post` | `C-POST` | single | confidence-post ("Looking back"); optional reflective-bridge |
| 5 | `wrapper-close` | `W-CLOSE` | single | summary, practice-connection, where-next, course-references |

- `pageSet.fixedPages` holds the W-OPEN/C-PRE/SUMM/C-POST/W-CLOSE order;
  `lessonInsertionPoint` places the variable-count lesson pages between C-PRE and SUMM.
- `articleSections.multiArticlePageTypes = ["lesson"]`; everything else is single-article.
- Block-ID rule: `<pageKey>-b-<NN>`, step 5, in render order.
- The canonical `config.json` baseline lives in the same file under `courseConfigBaseline.config`.

**Two other meanings of "shapes" — keep them separate:**

- **Content shapes** (`design-kb/design-kb.content-shapes.json`) — 15 information types
  (fact, concept, structure, classification, procedure, process, principle, contrast,
  parallel-options, pairs, error, assembly, judgement, criteria, reflection). These drive
  component routing, not page layout.
- **Activity patterns** (`design-kb/design-kb.activity-patterns.json`) — 18 pedagogy
  patterns that route a content shape → a component (§6).

## 3. Articles = phases (your intro / middle / end)

A **lesson** page is a fixed 5-article spine. Phase is encoded as a CSS class on the article:

| Article | `_classes` | Your phase |
|---|---|---|
| a-01 | `article--lesson-open` | **intro** |
| a-02 | `article--lesson-concept` | **middle** |
| a-03 | `article--lesson-formative` | **middle** |
| a-04 | `article--lesson-reflection` | **end** |
| a-05 | `article--lesson-close` | **end** |

`articleSections.sectionOrder = [lesson-open, lesson-concept, lesson-formative, lesson-reflection, lesson-close]`.
The SUMM article additionally carries a full `_assessment{}` block and `_trickle{}`.

**Block-role → article routing** (`articleSections.roleToSection`):

```
orientation, orientation-tier, learning-outcomes → lesson-open
concept, worked-example, practical-guidance       → lesson-concept
knowledge-check                                    → lesson-formative
reflective, reflective-task                        → lesson-reflection
summary, references                                → lesson-close
```

## 4. Custom fields — "what we called our fields"

These are the project's own additions on top of stock Adapt.

### On blocks (`en/blocks.json`) — the two signature keys
- **`_skeletonKey`** (string) — the block's structural role/slot. **This is the backbone of the engine.**
  Observed values: `overview, learning-outcomes, practice-connection, signpost,
  course-instructions, course-conventions, confidence-pre, confidence-post, orientation,
  orientation-tier, concept-definition, concept-context, concept-intro, worked-example,
  practical-guidance, check, reflective-prompt, summary, lesson-references, introduction,
  assessment-items, results, where-next, course-references`.
- **`_trackingId`** (int, unique per block) — SCORM suspend-data stability. A single dense
  counter across the whole course; `course.json._latestTrackingId` is the high-water mark (84 in undlaf-intro).

```json
{ "_id": "L01-b-15", "_parentId": "L01-a-02", "_type": "block",
  "title": "Concept: definition", "_trackingId": 9, "_skeletonKey": "concept-definition" }
```

### On components (`en/components.json`) — slot-provenance class + variant
- **`_classes` slot convention**: `slot__<pageKey>__<skeletonKey>[ extra-class]`, e.g.
  `slot__L01__worked-example`, `slot__L01__check knowledge-check-question`,
  `slot__wrapper-open__practice-connection`. Stamps each rendered component with the page + slot it was generated into.
- **`_variant`**: e.g. `"reflection"` on the opentext reflective prompts.
- Standard-but-notable fields in use: `_layout` ("full"), `_setCompletionOn` ("allItems"),
  `_diagram{src,title}` (ab-hotgraphic), `_pageLevelProgress`, and the confidence component's
  `_mode` / `_selfAssessmentGroupId`.

### On contentObjects (`en/contentObjects.json`) — tile/theme markers
- `_classes`: `cm-tile-soft`, `cm-tile-accent`, `cm-tile-icon-assessment`, `ab-has-title-icon`.
- Inline icon spans in `displayTitle`: `<span class="ab icon-learning-svg" aria-hidden="true"></span>…`.
- Every page carries a `_pageLevelProgress` block and `_graphic.src: "course/en/images/menu-item.png"`.

### On config (`config.json`) — theme-profile framing
- `_htmlClasses: "ab-theme ab-profile-ember cm-theme-dark-blue-grey ab-force-light"`
  (theme + profile + colour-scheme + light-force). `_fixes._imgLazyLoad`, `build.strictMode`.

### Portable-unit convention
Each lesson is a self-contained unit: `L0n-`-prefixed ids (vs slug-prefixed wrappers),
self-contained tracking, no sibling dependency. Wrapper framing is per-pathway-tier.
See `docs/authoring/portable-unit-and-shell-format.md`, `docs/authoring/wrapper-and-portability.md`.

## 6. The six-part flow → block sequence (how a lesson is built)

Pedagogical flow (CLAUDE.md): orientation → concept (example-first) → worked example →
analysis → practical guidance → reflective prompt. Realised as the lesson block spine:

| # | `_skeletonKey` | Flow stage | Article (phase) |
|---|---|---|---|
| 1 | `orientation` (+ `orientation-tier`) | orientation | lesson-open (intro) |
| 2 | `learning-outcomes` | orientation | lesson-open (intro) |
| 3 | `concept-definition` | concept (generic definition) | lesson-concept (middle) |
| 4 | `concept-context` | concept (subject recast) · `gateAfter:true` | lesson-concept (middle) |
| 5 | `concept-intro` | concept (interactive "explore") | lesson-concept (middle) |
| 6 | `worked-example` | worked example (weaker→stronger; analysis folded in) | lesson-concept (middle) |
| 7 | `practical-guidance` · `gateAfter:true` | practical guidance | lesson-concept (middle) |
| 8 | `check` (×3 MCQ, one per lesson outcome) | knowledge-check | lesson-formative (middle) |
| 9 | `reflective-prompt` (opentext, `_variant:"reflection"`) | reflective prompt | lesson-reflection (end) |
| 10 | `summary` | consolidation | lesson-close (end) |
| 11 | `lesson-references` | references | lesson-close (end) |

`gateAfter:true` = trickle gating ("now see it" / "now prove it"). Completion rules per role in
`skeletons.json → completionRules` (reading roles complete on view; checks on submit-resolved;
reflective on submit, optional/non-blocking).

## 7. Component-routing logic (how the engine picks a component for a slot)

`gate → content-shape → activity-pattern → palette component → authored with facet-triggered grounding`

1. **Shape first** — name the content shape(s) for the slot (`design-kb.content-shapes.json`),
   quoting the book passage.
2. **Candidates** — from `design-kb.activity-patterns.json`, every pattern whose `servesShapes`
   includes the shape, whose `intent` admits the gate intent, whose `tierCalibration` fits the
   course tier, and whose `slotTypes` includes the slot. Rank by `contextAffinity` vs `manifest.facetSet`.
3. **Realisation** — the pattern's `realisations[].component` = a `palette/*` id; pre-flight against
   its `specPointer` spec doc.
4. **Slot definition** — `design-kb.skeletons.json` gives each slot a `selectionModel` and
   `contextCoupling` (shell-coupled / token-substitution / structured-fields / whole-prose).
5. **Agent direction** — slots with an `agentAuthor` block resolve via `tools/resolve-agent-author.js`,
   applying only the steers whose facet is active (tier always; subject/qualifier/institution once set).

Example pattern routings: `retrieval-practice → check → [mcq, sortable]`;
`explore-model → concept-intro/worked-example → [hotgraphic, ab-hotgraphic, narrative, timeline, flipcard, accordion, graphic, media]`;
`write-own-thinking → reflective-prompt → [opentext]`; `action-checklist → [checklist]`.

## 8. Styling / theme (for when you style the generated templates)

- **Editable source of truth:** `src/extensions/adapt-ab-theme/less/` — notably
  `ab-cards.less` (cards), `ab-buttons.less` (buttons), `ab-schemes.less`, `ab-palette.less`,
  `ab-semantics.less`, `ab-type.less`, `ab-callouts.less`, `ab-colour-profiles.less`,
  `cmab-theme-packs.less`, `L1-adapt-vanilla-hooks.less`; plus `src/extensions/adapt-ab-navigation/`.
- **The structural "spine" selector map** you style against:
  `tools/theme-mapping/layers/ad-layers/l0-adapt-templates/adapt-template-classes.less`
  (generated — do not hand-edit; 15-rung spine html#adapt → … → .component__widget, then every
  component's selectors).
- **Computed CSS outputs:** `exports/theme-css/` (incl. `ab-cards.css`, `ab-buttons.css`,
  `ab-callouts.css`, `ab-colour-profiles.css`, …) produced by `tools/adapt-ab/ab-theme-css.js`
  + `ab-theme-computed.js`.
- Extension CSS (nav/buttons/theme) compiles in phase 3 of the LESS cascade and is **not** captured
  by the l0 template-classes generator — style those classes directly in the extension `less/`.
