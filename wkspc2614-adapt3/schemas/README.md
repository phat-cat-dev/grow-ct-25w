Schemas — Session 1 output (15 Aug 2026, validated 26 Aug via AW:Intro retro-fill)

Two stores, one manifest:

design-kb/ — internal, self-authored design knowledge. Six files (palette, tier-bands, skeletons, gates, activity-patterns, content-shapes) each carrying its own kbVersion (design-kb/manifest.json does not exist; see backlog 5.94) (shape defined in common). activity-patterns holds the pedagogical constructs proposals are made IN TERMS OF (pattern = pedagogy; component = mechanism; slot = location), covering formative and summative activity types including future activity-based SUMM variants. content-shapes (design-kb.content-shapes.json / design-kb.content-shapes.schema.json, CS-1, Prompt 124) names the shapes book content takes — seven anchored on Horn's Information Mapping types, eight academic-skills extensions — read by the design process before an activity pattern is proposed, and by the book scan to tag content. Sibling to content-conventions but a different job: content-conventions records how built courses wrote their content; content-shapes is what the design process and book scan read.
source-kb/ — EXTERNAL PUBLISHED authority material (sector frameworks FHEQ/CQFW, QAA subject benchmarks, subject literature) — public, versioned by its issuers.
institutional-kb/ — INSTITUTION-SUPPLIED material (faculty/school guidance, module documents, programme lists). Multi-institution: entries carry an institution identifier; Cardiff Met is the first tenant, not the definition. Not public; obtained through relationships, sensitivity handled accordingly. Internal entry formats landed Session 4 (see source-kb.schema.json / institutional-kb.schema.json); common citation conventions still govern how entries are cited FROM elsewhere (gate grounding, manifest).
source-kb.schema.json — entry index for external published sources (FHEQ/CQFW, QAA benchmarks, subject literature); designed S4, see open-decisions S4-1.
institutional-kb.schema.json — entry index for institution-supplied sources (guidance, module docs, programme lists); multi-institution, sensitivity first-class; designed S4, see open-decisions S4-1.
course-design.json — one per course: the manifest of decisions. Declares archetype instantiations, slot choices, facet set, and every gate outcome with provenance. Never contains content or structure bodies (S1-D5).

Level is an independent contextual facet — present without any institutional attachment; institutional facets may constrain it (module -> singleton, faculty/school -> range) but never bring it. kbVersion bump policy (2 Sep 2026): any amendment to a design-kb store bumps its kbVersion patch number. Citations record the version current at decision time. Pre-policy citations (all existing 0.1.0 and 0.0.0 references) are NOT version-discriminating — the store may have changed beneath them — and are left as recorded rather than rewritten, per the annotate-don't-rewrite discipline. No tooling enforces this; it is discipline, not a constraint.
Concept ordering (recorded 10 Oct 2026; exercised, not yet human-ratified). A catalogue/reference file orders its top-level keys by CONCEPT — a deliberate reading order from identity outward — never alphabetically or by when a field was added. The per-pathway reference (catalogue.pathway-reference) reads identity → capabilities → tierProgression → theorySpine → crossCutting → gaps (then the v2 adaptIntegration / bookGrounding, then source); the shared cross-cutting store (catalogue.cross-cutting) reads tierModel → genericLadder → frameworks → crossCuttingThemes → developmentModels (then source). The order is part of the contract: a generator writes keys in it and a reader relies on it, so the files stay legible as they grow. Each file's schema `description` states its own order. Exercised by catalogue.pathway-reference and catalogue.cross-cutting (property order verified against both schemas, 10 Oct 2026).
Dual axes (recorded 10 Oct 2026; exercised, not yet human-ratified). Every tiered row carries BOTH axes as first-class fields: our own tier (introductory / intermediate / advanced) and the single indicative FHEQ level (`fheqLevel`). The two are never collapsed into one. The tier↔level relationship itself — the overlap formula and the full row grid — is stated ONCE, in the shared cross-cutting store's `tierModel`, and is NEVER duplicated per row; a per-row cell carries only its own `tier` + `fheqLevel` and points back to that spine. Exercised by catalogue.cross-cutting (`tierModel`, "both axes first-class"), catalogue.pathway-reference ("every tiered item carries both axes … per the shared cross-cutting store") and catalogue.subject-benchmark (tierReadings rows require `tier` + `fheqLevel`; the overlap formula is explicitly not per row).
Agent-direction metadata (PATTERN; PROPOSED, not binding). Instruction metadata that steers an AI authoring agent lives in the DATA MODEL, machine-readable, and never in the rendered DOM (which would leak to learners and bloat SCORM). Today one flat string, `standingContextPrompt`, sits on each coupled skeleton slot in design-kb.skeletons.json. The generalised pattern — a layered `agentAuthor` block (a mode-agnostic baseline plus `written` / `dialogue` mode variants, selected by (tier, mode) and resolved most-specific-wins across skeleton → manifest, warnings accumulating and directives overriding) — is specified in `docs/authoring/agent-author-metadata.md`. It is a PROPOSAL: it does not become a binding convention until landed through that doc's Governance route (a design-kb.skeletons.json kbVersion bump plus a tools/validate-design-schemas.py rule, and, for manifest-level fields, a gate record rather than a hand-edit). Named here so the pattern sits alongside the other conventions, with its not-yet-landed status explicit.
